## 1. Задача

Перестроить систему обнаружения обращения к Юми по принципу простого и быстрого
Wake Word Engine.

**OpenWakeWord с существующей моделью `yumi.onnx` должен стать единственным
основным механизмом обнаружения имени «Юми».**

Убрать из контура ожидания обращения:
- Vosk как дополнительный детектор имени
- Фонетический поиск имени через Vosk
- EARVETO
- Nemotron как судью обнаружения имени
- Whisper как судью обнаружения имени
- Дополнительные цепочки проверки имени после срабатывания OpenWakeWord

Vosk, Nemotron и Whisper сохранить для распознавания команды **ПОСЛЕ** пробуждения,
существующая конфигурация `stt_engine` не меняется.

Не заменять существующую ONNX-модель и не переобучать её.

После аудита предоставить краткую карту существующей архитектуры и план изменений.

## 3. Архитектура

### Текущая (старая, до миграции)

```
Микрофон
  |
  v
AEC (эхо-подавление)
  |
  v
HPF (высокочастотный фильтр)
  |
  v
Кольцевой буфер (~8 с)
  |
  +---> VAD ---> Vosk (конец фразы) ---> Whisper/Nemotron (судья имени)
  |
  +---> OpenWakeWord (предфильтр, оценка кадра)
  |
  v
Arbiter.decide (ранг: >=0.7 сразу, 0.5-0.7 судье, иначе игнор)
  |
  v
Пробуждение -> STT -> brain.py -> HTTP API
```

### Целевая (новая, по yumi-wake-engineb.md)

```
Микрофон
  |
  v
AEC (эхо-подавление собственного голоса)
  |
  v
HPF (удаление низкочастотного гула)
  |
  v
Кольцевой аудиобуфер (~8 с)
  |
  +-------> VAD (экономия ресурсов, не блокирует обращения)
  |         |
  |         v
  |      OpenWakeWord yumi.onnx  (единственный детектор имени)
  |         |
  |         v (score >= порога)
  |      ПРОБУЖДЕНИЕ
  |         |
  |         v
  |      STT (Vosk/Nemotron/Whisper по stt_engine) — только хвост фразы
  |         |
  |         v
  |      brain.py -> HTTP API
  |
  +-------> Исходный буфер продолжает писаться (для восстановления начала фразы)
```

### Состояния

- **SLEEP** — спит, ждёт имени «Юми» через OpenWakeWord
- **LISTENING** — проснулась, слышит команду (STT активен)
- **SPEAKING** — говорит (TTS), уши приглушены (mute), STOP работает независимо

## 8. Известные риски и ограничения

- **Ложные срабатывания на музыке и видео** — главный риск oww. Судью не выключать на ранних этапах.
- **Клиппинг микрофона** глушит модель: тот же клип с колонок на горячем тракте — 0.17–0.36, чистый — 0.94. Усиление уже сбавлено (Boost 1 / Capture 38 / Digital 85).
- **Recall на живом голосе — пограничный:** максимум по ленте пользователя 0.62–0.80; вживую при пороге 0.4 пробник поймал «юми» (0.66).
- **Модель ждёт 16 kHz mono s16** — путь записи ушей совпадает (echo-cancel чистый поток, `yumi_ec`), менять ничего не надо.
- **oww-модели обучаются в Colab; локально на CPU — медленно.**
- **oww ≥ 0.7 в растяжке — имя без судьи; 0.5–0.7 — лента уходит судье** (промежуточное состояние, к концу миграции судью убрать).
- Не заменять существующую ONNX-модель и не переобучать её.

## 11. Главный принцип

Не усложнять систему без необходимости.

Одна модель OpenWakeWord должна отвечать за обнаружение имени.

VAD должен помогать экономить ресурсы, но не блокировать настоящие обращения.

STT должен запускаться после пробуждения.

STOP должен работать независимо от основного состояния.

Сначала изучить проект, затем реализовать архитектуру, затем провести сравнительные испытания.

Не ограничиваться планом или псевдокодом — внести реальные изменения в репозиторий, запустить тесты и предоставить работающую реализацию.
