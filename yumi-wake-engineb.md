# ЗАДАНИЕ ДЛЯ CODE AGENT
# YUMI WAKE ENGINE — новая архитектура голосовой активации

## 1. Контекст проекта

Работа ведётся в отдельной Git-ветке. Основная ветка должна остаться нетронутой.

В проекте Yumi уже существует голосовая инфраструктура:

- stt_daemon.py — демон обработки аудио.
- oww_ear.py — отдельный процесс обнаружения ключевого слова.
- yumi.onnx — обученная модель обнаружения имени «Юми».
- Vosk — распознавание речи.
- Nemotron 0.6B — дополнительный механизм распознавания.
- Whisper Small — альтернативный STT.
- yumi_ec — эхоподавление собственного голоса.
- HPF, VAD, gate_noise — обработка аудиосигнала.
- Кольцевой аудиобуфер примерно на 8 секунд.
- brain.py — обработка команд.
- TTS — синтез речи.
- HTTP API между STT и brain.

Точные названия, расположение и назначение файлов необходимо проверить самостоятельно.

## 2. Главная задача

Перестроить систему обнаружения обращения к Юми по принципу простого и быстрого Wake Word Engine.

OpenWakeWord с существующей моделью yumi.onnx должен стать единственным основным механизмом обнаружения имени «Юми».

Убрать из контура ожидания обращения:

- Vosk как дополнительный детектор имени.
- Фонетический поиск имени через Vosk.
- EARVETO.
- Nemotron как судью обнаружения имени.
- Whisper как судью обнаружения имени.
- Дополнительные цепочки проверки имени после срабатывания OpenWakeWord.

Все эти механизмы не должны участвовать в принятии решения о пробуждении.

Vosk, Nemotron и Whisper сохранить для распознавания команды ПОСЛЕ пробуждения, согласно существующей конфигурации stt_engine.

Не заменять существующую ONNX-модель и не переобучать её.

## 4. Новая архитектура

Целевая схема:

МИКРОФОН
  |
  v
PipeWire / ALSA
  |
  v
Аудиозахват
  |
  v
AEC — эхоподавление собственного голоса
  |
  v
HPF — удаление низкочастотного гула
  |
  +-----------------------------+
  |                             |
  v                             v
Исходный аудиобуфер         Мягкая очистка
  |                             |
  |                             v
  |                            VAD
  |                             |
  |                             v
  |                       OpenWakeWord
  |                         yumi.onnx
  |                             |
  |                             v
  |                         WAKE EVENT
  |                             |
  +-----------------------------+
                |
                v
        Извлечение фразы
                |
                v
       Vosk / Nemotron / Whisper
                |
                v
             brain.py
                |
                v
               TTS

Отдельный независимый канал:
МИКРОФОН → AEC → STOP DETECTOR → остановка TTS и текущих действий.

Это целевая логика. Фактическую реализацию потоков адаптировать к существующему коду.

## 5. Работа в режиме ожидания — SLEEP: VAD как оптимизация, а не фильтр

Главное архитектурное требование:

**VAD НЕ должен иметь права блокировать обнаружение ключевого слова OpenWakeWord.**

OpenWakeWord должен сохранять возможность обнаружить «Юми» даже тогда, когда VAD не определил речевую активность.

VAD используется исключительно для оптимизации вычислительной нагрузки.

### Принцип работы

1. Микрофон постоянно передаёт аудио.
2. AEC и необходимая подготовка сигнала работают постоянно.
3. Аудио поступает в кольцевой буфер.
4. VAD оценивает наличие речи.
5. OpenWakeWord анализирует аудио независимо от решения VAD.

### Адаптивный режим OpenWakeWord

Предусмотреть два режима:

**Режим A — VAD обнаружил речь:**
- OpenWakeWord работает с обычной частотой проверки.
- Используется стандартная чувствительность.
- Обнаружение имени происходит без дополнительных проверок Vosk.

**Режим B — VAD не обнаружил речь:**
- OpenWakeWord НЕ отключается.
- Не прекращается передача аудио.
- Не сбрасывается состояние модели.
- Не блокируется накопление аудиоконтекста.
- Допускается снижение частоты дополнительных вычислений, если это не нарушает непрерывность обработки и требования модели.

ВАЖНО: нельзя просто пропускать аудиокадры OpenWakeWord, если это нарушает ожидаемую последовательность входных данных или внутреннее состояние модели.

Если необходимо экономить CPU, использовать штатный механизм оптимизации инференса, а не разрывать временную последовательность аудио.

### Запрещённая реализация

НЕ реализовывать такую логику:

if not vad_speech:
    continue

или:

if not vad_speech:
    skip_openwakeword()

Она приведёт к пропуску тихих обращений, коротких слов и речи на границе чувствительности VAD.

### Дополнительные требования

- VAD не принимает окончательного решения о наличии обращения.
- VAD не управляет разрешением на пробуждение.
- VAD не может вызвать EARVETO или аналогичный запрет.
- OpenWakeWord получает непрерывную последовательность корректных аудиоданных.
- При отсутствии VAD-активности OpenWakeWord продолжает обнаружение имени.
- После обнаружения имени VAD используется для определения окончания фразы.

### Проверочные тесты

Обязательно проверить:

1. Тихое произнесение «Юми», когда VAD не активировался.
2. Короткое произнесение «Юми».
3. Произнесение имени на фоне тихой музыки.
4. Произнесение имени издалека.
5. Произнесение имени с низким уровнем громкости.
6. Непрерывную работу OpenWakeWord при длительной тишине.

Критерий готовности:

**Ни одно отрицательное решение VAD не должно само по себе приводить к невозможности обнаружения имени OpenWakeWord.**

VAD оптимизирует нагрузку, но не определяет, имеет ли Юми право услышать пользователя.

## 6. OpenWakeWord

Использовать один экземпляр OpenWakeWord и одну модель yumi.onnx.

Требования:

- Не загружать ONNX-модель заново на каждом аудиокадре.
- Не создавать несколько параллельных экземпляров модели.
- Использовать последовательную обработку кадров.
- Не терять аудиокадры.
- Не допускать накопления очереди аудио при перегрузке.
- Корректно обрабатывать пустые и повреждённые аудиоблоки.
- Сохранять временные метки обработки.

Проверить, что аудио передаётся модели в правильном формате.

Порог обнаружения вынести в конфигурацию.

Не использовать порог 0.7 автоматически только потому, что он использовался в старой системе.

Провести калибровку на существующих записях.

Предусмотреть:
- activation_threshold;
- удержание обнаружения;
- cooldown;
- подавление повторных событий;
- минимальную продолжительность совпадения, если она поддерживается реализацией.

Не считать единичный случайный всплеск score достаточным для пробуждения.

При этом не вводить чрезмерную задержку подтверждения имени.

Сохранять score для диагностики.

## 7. Режим LISTENING

После обнаружения имени:

1. Создать событие WAKE.
2. Зафиксировать временную метку пробуждения.
3. Извлечь аудио из кольцевого буфера.
4. Сохранить часть аудио до обнаружения имени.
5. Продолжить захват последующей речи.
6. Дождаться окончания фразы по VAD.
7. Передать полную фразу в существующий STT.
8. Передать результат в brain.py.

Особенно важно:

Пользователь может произнести:

«Юми, включи музыку».

OpenWakeWord может сработать уже после начала слова «Юми».

Нельзя отрезать начало фразы или терять слово «включи».

Необходимо корректно собрать:

- аудио до обнаружения;
- аудио во время обнаружения;
- аудио после обнаружения.

Сохранять исходные временные метки.

После окончания речи использовать существующий механизм VAD endpointing.

Сохранить текущую логику:
- 1.2 секунды тишины для окончания обычной фразы;
- 1.5 секунды для отдельного произнесения имени, если эта логика используется.

Не менять поведение без необходимости.

## 8. Режим SPEAKING

Во время TTS:

- Микрофон продолжает работать.
- AEC продолжает работать.
- OpenWakeWord не должен пробуждать Юми от её собственного голоса.
- Необходимо учитывать остаточные ошибки эхоподавления.
- Не отключать физически весь микрофонный тракт.

Можно временно отключать или повышать порог основного детектора во время TTS, если это необходимо.

Но нельзя полностью потерять возможность прерывания Юми пользователем.

После завершения TTS:
- восстановить обычную чувствительность;
- сбросить устаревшие данные аудиобуфера, если они содержат только собственный голос;
- не потерять речь пользователя, начавшуюся непосредственно после TTS.

## 9. Независимый канал STOP

Команда «стоп» должна работать в любом состоянии:

- SLEEP;
- LISTENING;
- SPEAKING.

Особенно важен сценарий:

Юми говорит:
«Сейчас я включу музыку...»

Пользователь перебивает:
«СТОП!»

Юми должна немедленно прекратить TTS и текущую операцию.

Проверить существующий механизм распознавания STOP.

Не считать отключённый Vosk во время TTS полноценной реализацией этой функции.

Реализовать отдельный лёгкий механизм обнаружения команды STOP, если существующая система не обеспечивает её надёжно.

Не использовать тяжёлую LLM для остановки.

Защитить STOP от ложных срабатываний на собственную речь Юми.

## 10. Кольцевой буфер

Сохранить существующий кольцевой буфер.

Проверить его корректность.

Требования:

- Не менее 5–8 секунд истории.
- Небольшой фрагмент до имени.
- Сохранение всей команды после имени.
- Корректная синхронизация между аудиопотоками.
- Защита от чтения одновременно изменяемого буфера.
- Отсутствие потери данных на границе кольца.
- Корректное поведение при переполнении.

По возможности использовать единый временной базис для всех событий.

Не копировать весь буфер без необходимости.

## 19. Главный принцип

Не усложнять систему без необходимости.

Одна модель OpenWakeWord должна отвечать за обнаружение имени.

VAD должен помогать экономить ресурсы, но не блокировать настоящие обращения.

STT должен запускаться после пробуждения.
